# 目录库重建记录

> 执行日期：2026-09-19　|　库：`电子取证标准目录（候选）`（`1e96bd2aadd611f19c1d47fabda44d24`）
> 工具：`rebuild_catalog.py`（本目录）

## 一、为什么要重建

目录库的卡片**不是一次性产物**——`build_standard_cards.py` 每次运行都会重写
`11-标准卡片索引/` 下的全部卡片。本次之前有两条线改动了卡片内容：

1. **标准状态核验**（见 `17-AC标准状态核验.md`）：14 条候选标准的状态、发布/实施日期、
   替代关系、官方来源 URL 被回写，卡片里 `标准状态` 由「待权威核验」变为「现行」或「废止」。
2. **卡片渲染模板调整**：目录层条目现在也输出官方来源、发布与实施、替代关系、
   核验日期与备注，「可否作为主推荐」改为按原因分述。

线上目录库还停留在旧内容，因此**查询时拿到的是过期状态**——
最典型的危害是**已废止的标准仍显示为可用**。

## 二、为什么必须「先清后传」

正文库是「有则跳过」的增量导入；目录库不能照搬，因为：

- RAGFlow 对**同名文件不会覆盖**，而是存成 `xxx(1).md`。
  直接重传会让同一标准在库里出现两份，检索时互相稀释评分。
- 卡片文件名（`ga-t-1069-2021.md`）是按标准编号生成的，天然唯一，
  所以「删干净 → 重传」是唯一能保证一份标准只有一条记录的做法。

`rebuild_catalog.py` 因此提供 `--purge`：先清空，再上传，并在清空后
**校验库确已为空**（有残留就中止，避免产生重名副本）。

## 五、备份与回滚

导出脚本在 `ragflow-query/logs/` 下产出：

```text
目录库备份-20260919-171720.json     86.7 KB，85 份文档，0 份内容为空
```

结构：`{dataset_id, exported_at, documents: [{id, name, chunk_count, run, content}]}`，
`content` 为该文档全部切片拼接的原文。

**回滚方式**：清空当前库后，按备份里的 `name` + `content` 重建文件再上传解析。
备份**不包含**向量（重新解析即重建），也不包含归属的其他元数据。

## 六、本次踩到的两个问题

### 1. 一份文档解析失败，重发即过

`ga-t-1568-2019.md` 首轮 `progress=-1.0 / chunks=0`。检查卡片本身
（832 字节、18 行、格式与同类完全一致）后确认**不是数据问题**，
单独重发 1 次即成功。

这与正文库的结论一致：**并发解析时 embedding 端会偶发单份失败，
单独重发必过**（见 README「关键发现」第 8、9 条）。
脚本已内置「批内失败 → 单独重试」，本次正是靠它收尾。

### 2. `wait_batch` 的统计缺陷（已修）

首轮汇总报「解析成功 38」，但线上实际 87 份中 86 份正常——
差在 `wait_batch` 一旦发现失败文档就**立即返回**，同批其他仍在解析的文档
被漏计。已改为**等整批都到终态再返回**：

```python
if done + len(failed) == len(doc_ids):
    return (not failed), failed
```

`rebuild_catalog.py` 与 `import_texts_to_ragflow.py` 两个脚本均已同步修正。
（此缺陷只影响报告数字，不影响实际入库结果——RAGFlow 会继续异步解析。）

### 3. `knowledgebase.chunk_num` 比实际多 3（不影响检索）

重建后两处统计对不上：

| 口径 | 值 |
| --- | --- |
| `knowledgebase` 表 `doc_num` / `chunk_num` | 87 / **90** |
| `document` 表 `COUNT(*)` / `SUM(chunk_num)` | 87 / **87** |
| 逐份 API `chunk_count` 求和 | 87 |

RAGFlow 的 `knowledgebase.chunk_num` 是解析/删除时**增量累加维护**的计数器
（并非实时统计），删除 85 份旧文档时没有完全减净，于是多出 3。

**已实测确认不影响检索**：用 12 个泛化查询（「标准」「检验」「法庭科学」等）
对目录库做探针，命中的 `document_id` 去重后恰好是 **87 个**——
全部属于当前库内文档，**0 份未命中，无孤儿切片**。

结论：这是计数器的显示口径问题，**不是数据残留**。
核对库存请以 `document` 表为准，不要用 `knowledgebase.chunk_num`。

> 附带发现：`/api/v1/retrieval` 的 `page_size` **不能超过库内切片总数**，
> 否则报 `code=102`：`` `rerank_candidates_count` must be at least `page` multiplied by `page_size` ``。
> 对只有 87 个切片的目录库请求 `page_size=100` 就会触发。查询应用用的是 8，不受影响。
